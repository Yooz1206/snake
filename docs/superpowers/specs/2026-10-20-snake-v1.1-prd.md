## 0. 摘要

### 0.1 一句话

把 Snake 从"一局就走的作品"变成"每天 60 秒的固定休息"：**每天同一开局、三次机会、一键分享战绩**，同时保持零依赖、零后端、零个人追踪。

### 0.2 问题

v1.0 的手感与工程质量明显高于同类，但作为产品，它缺三样东西：

1. **回访理由**：没有每日内容，玩家没有"明天再来"的理由。
2. **传播载体**：最高分只存在本机，无法成为社交货币；分享链接没有预览图，发出去只是一条裸链接。
3. **承诺兑现**：页面和 `package.json` 都写了"离线可玩"，但没有 Service Worker 和 manifest，离线是否可用完全取决于浏览器缓存。

### 0.3 方案：只做三件事

| # | 做什么 | 为什么是它 |
| --- | --- | --- |
| 1 | **每日挑战**：日期种子、同一开局、每天 3 次机会、连续天数 | 用最低成本制造"明天再来"的理由，不需要账号和后端 |
| 2 | **战绩分享**：本地生成分享卡 + Web Share / 下载 / 复制 | 把分数变成社交货币，让每一次分享都带来新玩家 |
| 3 | **真离线**：manifest + Service Worker，可安装、可离线 | 兑现已有承诺；顺带修复"发出去没预览"的分享体验 |

配套修复四类"承诺级"缺陷：最高分在切标签时丢失、移动端首屏提示与实际交互不一致、暂停恢复后立即死亡、次要文字对比度不达标。

三件事按依赖顺序推进：①每日挑战（R1）制造回访理由；②战绩分享（R2）把回访转成拉新；③真离线/PWA（R3）兑现已有承诺，并顺带补上链接预览。三者共用同一套本地状态与日期种子，不引入后端。

### 0.4 成功标准

| 维度 | 指标 | 目标 |
| --- | --- | --- |
| 习惯 | 每周完成 ≥3 次每日挑战的玩家占比 | ≥ 25%（7 天 cohort，n≥20） |
| 传播 | 每日完成者中实际触发分享的比例 | ≥ 15% |
| 留存 | 次日回访率 / 7 日回访率 | ≥ 30% / ≥ 12% |
| 工程 | 首屏 LCP / INP / CLS | ≤ 1.0s / ≤ 100ms / ≤ 0.02 |
| 品质 | Lighthouse 移动端 Performance / Accessibility | ≥ 95 / ≥ 95 |
| 护栏 | 第三方网络请求、分享泄题、首屏体积回退 | 0 / 0 / ≤ 50% |

> 这些是**待验证的假设目标**，不是历史基线。v1.0 上线仅一天，没有可用的留存数据；测量方案见 5.5。

### 0.5 不做什么

不做账号、云存档、全球排行榜、多人对战、皮肤商店、广告、推送、每日签到、体力值、原生 App。

### 0.6 需要拍板的三件事

| # | 待拍板项 | 建议 | 不拍板的后果 |
| --- | --- | --- | --- |
| 1 | 每日次数 = 3 是否定档（OQ1） | 定 3；cohort 后再调 | R1 状态机与 UI 文案无法冻结 |
| 2 | 分享卡是否显示"第 N 次"（OQ2） | 显示，增强可比性 | R2 卡面与 canvas 绘制无法定稿 |
| 3 | 北极星指标在 7 天 cohort 内无法计算，是否接受 T14 才复盘 | 接受；T7 只看 M1–M5 | 验收节奏与发布计划对不齐 |

以下三件事若不拍板，工程无法在 M1 启动；建议评审会上一次性确认：

| # | 决策 | 建议 | 代价 |
| --- | --- | --- | --- |
| D1 | 每日挑战给几次机会 | **3 次** | 比无限次更有 stakes；比 1 次更宽容 |
| D2 | 是否引入埋点 | **不引入** | 指标只能靠小样本验证；换取"零追踪"的品牌一致性 |
| D3 | "同一开局"如何定义 | **相同日期种子 + 相同初始状态；相同输入序列产生相同状态** | 不同走法会导致后续食物位置不同，不能承诺"逐帧同一关" |

## 1. 背景与问题

### 1.1 现状：一个完成度很高的作品

![图 1 · v1.0 线上界面（左：开始；右：进行中）](assets/snake-ui.png)

v1.0 于 2026-10-19 上线 GitHub Pages，是一个零依赖、无构建步骤的静态站点：

| 维度 | 现状 | 依据 |
| --- | --- | --- |
| 体积 | HTML + CSS + JS 合计 **29,854 字节**（未压缩） | 线上资源实测 |
| 依赖 | 运行时零依赖，无框架、无字体、无 CDN、无统计 | `package.json`、源码 |
| 规则 | 24×24 棋盘，初始长度 4，130ms/格，每吃一个加速 3.5ms，下限 72ms，每个 10 分 | `js/config.js` |
| 手感 | 固定步长 + 插值渲染；输入缓冲 2 次；拒绝反向 | `js/timestep.js`、`js/game.js` |
| 测试 | 17 个单元测试，覆盖碰撞、生长、缓冲、速度下限、随机走位 | `test/` |
| 视觉 | 深色霓虹、程序化音效、粒子与震屏、尊重 `prefers-reduced-motion` | `css/style.css`、`js/renderer.js` |
| 数据 | 最高分与静音状态存 `localStorage`，无账号 | `js/main.js`、`js/audio.js` |
| 隐私 | 无任何第三方请求、无埋点 | 源码全文 |

它的问题不是"做得不够好"，而是"做得像一个作品，不像一个产品"。

### 1.2 三个具体问题

**问题 1：没有回访回路。**玩家打开、玩一局、死掉、关掉。第二天没有新内容，最高分也不会驱动他回来。经典模式的所有变量（棋盘、速度曲线、食物随机）在第二局就重复了。

**问题 2：没有传播回路。**最高分只在本机。玩家想证明"我今天很厉害"，只能截图或口头说；链接发到群里没有预览图，也没有"来玩今天的每日挑战"的钩子。产品没有把一次游玩转化成一次拉新。

**问题 3：承诺与实现有裂缝。**`index.html` 的 meta description、`package.json` 的 description 都写了"offline support"，但仓库没有 `manifest.webmanifest`、没有 Service Worker。首次访问后能否离线打开，取决于 GitHub Pages 的缓存头与浏览器启发式缓存，**不可控、不可承诺**。同时 README 把"Accessibility"列为特性，但 10–12px 的次要文字对比度只有 **3.54:1**（WCAG AA 要求 4.5:1），静音按钮只有 **34×34px**（推荐 ≥44×44px）。

### 1.3 证据与假设

| 类型 | 内容 | 强度 |
| --- | --- | --- |
| 事实 | 无每日模式、无分享、无 PWA、无 OG 预览、无埋点 | 强（源码可查） |
| 事实 | 最高分只在死亡时写入；运行中刷新/切走会丢失新纪录 | 强（`commitBest()` 只在 `die` 事件调用） |
| 事实 | 移动端首屏提示"可滑动屏幕操作"，但滑动监听只绑在 canvas 上，而 ready 态 overlay 覆盖了 canvas | 强（`input.js` + `.overlay` 层级） |
| 事实 | 无胜利状态：棋盘填满后 `spawnFood()` 返回 `null`，游戏继续但没有食物 | 强（`game.js`） |
| 假设 | 目标用户中有相当比例愿意"每天花 60 秒玩一局每日挑战" | 中；需 cohort 验证 |
| 假设 | 分享卡能带来 ≥10% 的链接点击回流 | 中；需带 `?from=share` 观察 |
| 假设 | 玩家更在意"同一开局的可比性"而不是"无限随机" | 中；需 A/B 或访谈 |
| 反证 | 一部分玩家只想偶尔玩一局，任何"每日"设计都会被感知为任务 | 中；用练习模式和非强制入口缓解 |

### 1.4 问题陈述

> 对于想在碎片时间里玩一局高质量小游戏的人，Snake 提供了同类中最好的手感，但没有给他一个明天再来的理由，也没有给他一个把成绩分享出去的方式。结果是：每一次游玩都是一次性消耗，产品无法积累玩家，也无法自我传播。

### 1.5 为什么是现在

- **没有存量包袱**：上线一天，没有需要兼容的账号体系、排行榜或付费结构。
- **成本极低**：每日种子、分享卡、Service Worker 都不需要后端，符合"零依赖"的工程美学。
- **窗口很短**：一个作品上线后若两周内没有形成回访，它就会稳定地停留在"作品集里的一个链接"。现在加回路，成本最低。

## 2. 产品愿景与策略

### 2.1 愿景

> **让全世界最克制的一局贪吃蛇，成为每天 60 秒的固定休息。**

不是"最好玩的贪吃蛇"，也不是"内容最多的贪吃蛇"，而是**最值得每天打开一次的那一局**。

### 2.2 产品原则

| # | 原则 | 含义 | 违反示例 |
| --- | --- | --- | --- |
| P1 | **60 秒闭合** | 一局从开始到结束不超过 90 秒，随时可以停 | 加入需要连续游玩 10 分钟的关卡 |
| P2 | **零依赖、零后端、零个人追踪** | 运行时无第三方；数据只在本机；不发任何请求 | 接入统计 SDK、账号登录 |
| P3 | **手感优先** | 输入不丢、画面不抖、暂停不坑、恢复不死 | 为了动画增加输入延迟 |
| P4 | **克制** | 不催促、不弹窗、不签到、不制造焦虑 | "再玩一局解锁皮肤" |
| P5 | **可验证** | 每条规则有测试，每个承诺可复现 | 只在 README 里写"离线可用" |

### 2.3 策略：用"轻仪式"替代"重系统"

常见的留存手段是账号、排行榜、成就、每日签到。它们都需要后端、都会增加认知负担，也都与 P4 冲突。

v1.1 选择一条更轻的路：

```text
触发（每天 0 点刷新）
   → 行动（60 秒一局，三次机会）
      → 奖励（分数、连续天数、个人最佳）
         → 投入（分享战绩、明天再来）
```

这个回路的关键不是"更多内容"，而是**约束**：

- **同一开局**制造可比性："今天这局，大家都一样。"
- **三次机会**制造 stakes：不能无限重试，但也不至于一失误就放弃。
- **连续天数**制造轻量承诺：不需要推送，玩家自己会记得。
- **分享卡**制造社交货币：分数只有被看见才有意义。

### 2.4 为什么不是排行榜 / 成就 / 皮肤

| 方案 | 收益 | 成本/风险 | 决策 |
| --- | --- | --- | --- |
| 全球排行榜 | 强竞争、强传播 | 需要后端、账号、反作弊；会引入"刷分"和"外挂" | **不做**（v1.2 再评估） |
| 成就系统 | 中期目标感 | 与"60 秒一局"的轻量定位冲突；需要大量内容 | **不做** |
| 皮肤/主题 | 变现与个性 | 需要美术产能；会稀释"极简"品牌 | **不做** |
| 每日挑战 | 回访 + 可比性 + 分享 | 需要种子与本地状态，无后端 | **做** |
| 分享卡 | 传播 | 纯前端生成，无后端 | **做** |
| PWA/离线 | 兑现承诺 + 安装 | 一个 Service Worker 的维护成本 | **做** |

### 2.5 竞争与替代

| 产品 | 它赢在哪 | 它的空位 | 我们的回应 |
| --- | --- | --- | --- |
| Google Snake | 模式多、入口强、品牌 | 不是独立产品，入口藏在搜索里；无每日仪式 | 更轻、更快、更私密 |
| slither.io | 多人实时、社交强 | 需要网络、局时长、竞争压力大 | 单机、60 秒、无压力 |
| 经典 Nokia Snake | 怀旧、极简 | 手感与画面停留在过去 | 现代手感 + 同等克制 |
| Wordle | 每日一题 + 分享的教科书 | 不是动作游戏 | 借它的"每日 + 可分享结果"结构 |

**差异化一句话**：Wordle 的每日仪式，Nokia 的极简，现代 Web 的手感，且不追踪你。

### 2.6 商业与成功定义

Snake 是 MIT 开源、无广告、无内购的"作品型产品"，v1.1 **不设收入目标**。它的价值在三处：

| 价值 | 对谁 | 衡量 |
| --- | --- | --- |
| 作品信誉 | 作者、P1 手艺欣赏者 | 代码质量、文档、同行认可 |
| 分发资产 | 产品本身 | 一个能被记住、被分享、被收藏的链接 |
| 低成本实验 | 作者 | 验证"克制的每日游戏"能否形成习惯 |

因此本版的成功标准不是 ARPU、DAU 或融资故事，而是 **习惯玩家占比、分享率、以及"承诺是否兑现"**。如果未来要商业化，优先考虑不破坏体验的方式（赞助、周边、企业支持），而不是广告、内购或数据变现；那是另一份 PRD 的事。

## 3. 用户

### 3.1 目标用户

| 优先级 | 人群 | 典型画像 | 核心需求 | 成功的样子 |
| --- | --- | --- | --- | --- |
| P0 | **一分钟玩家** | 通勤、排队、会议间隙；手机为主 | 打开即玩、单手可玩、不装 App、不被广告打断 | 60 秒内完成一局，愿意明天再来 |
| P1 | **手艺欣赏者** | 开发者、设计师、独立游戏爱好者 | 看得到工程质量：零依赖、测试、60fps、细节 | 读完 README，点 star，转发给同行 |
| P2 | **群聊比较者** | Slack/Discord/微信群里的轻社交玩家 | 用一张卡证明"我今天不错" | 分享到群里，朋友点开就能玩当天的每日挑战 |

> 三类人不是互斥的。v1.1 的产品设计以 **P0** 为主，工程与文档的克制服务于 **P1**，分享卡服务于 **P2**。

### 3.2 Jobs to be Done

| 场景 | 用户想完成的事 | 现有替代 | 我们的价值 |
| --- | --- | --- | --- |
| 地铁上有一分钟 | "让我立刻玩点不用学的东西" | 短视频、消消乐、社交 feed | 零加载、零学习、离线可玩 |
| 工作间隙想换脑子 | "给我一个 60 秒能结束的挑战" | 刷手机、发呆 | 一局闭合，不拖泥带水 |
| 今天手感很好 | "我想让别人知道我今天的成绩" | 截图发群 | 一张不泄题、带链接的战绩卡 |
| 朋友发来一张卡 | "我也来试试今天的" | 点开链接玩普通模式 | 当天同一开局，直接可比 |

### 3.3 三个场景故事

**场景 A：离线通勤。**早上 8:15，地铁进隧道。她昨天把 Snake 装到了主屏。打开，今日挑战还剩 2 次。60 秒后死于撞墙，240 分，连续第 4 天。她把战绩卡存进相册，出站后发到群里。

**场景 B：桌面破纪录。**午休，他打开标签页，按空格开始。第 18 个食物后速度到达下限，蛇开始"滑"。他知道再吃一个就破自己的 380。手一抖，咬到尾巴。overlay 显示"咬到自己了 · 390 分 · 新纪录"，BEST 在运行中已经跳到 390。他按 R，再来一局。

**场景 C：群里被安利。**群里出现一张黑底绿字的卡："Snake 每日挑战 10月20日 · 240 分 · 连续 4 天"。他当天点开链接，页面直接是"每日挑战 · 10月20日"，不需要注册。第一局 80 分，第二局 260 分。他把自己的卡发回群里。

### 3.4 非目标用户

- 需要长期成长、装备、赛季、社交关系的重度玩家。

### 5.7 验证周期与 Go/No-Go 决策门槛

本节是 v1.2 评审新增，用于回答"什么时候、用什么数据、判定做成还是做不成"。

这是本 PRD 最重要的约束之一。v1.1 **不引入任何分析 SDK、Cookie、指纹或服务端日志**。原因：

1. "no tracking" 是 README 对用户的明确承诺，也是 P1 人群选择它的理由。
2. 一个聚合计数器也需要服务端与隐私政策，成本高于本版收益。
3. 上线初期样本极小，统计显著性不如直接观察 20 个人。

因此采用三层验证：

| 层级 | 方法 | 能回答什么 | 不能回答什么 |
| --- | --- | --- | --- |
| L1 工程 | `node --test`、CDP 冒烟、Lighthouse、离线/兼容矩阵 | 承诺是否兑现 | 用户是否喜欢 |
| L2 定性 | 20 人、7 天 cohort：首次任务观察 + 每日 1 分钟日记 + 结束访谈 | 回访、分享意愿、卡点 | 大样本显著性 |
| L3 公开信号 | GitHub star/fork/referrer、issue、分享链接回流（低置信） | 是否有人愿意传播 | 留存 |

**决策记录 D2**：如果 v1.2 要把增长作为主目标，再单独评审"隐私友好的聚合计数"方案（无 Cookie、无 ID、不存 IP、可退出），不在这版偷偷加。

### 5.6 反作弊与噪声

说明：北极星必须满 14 天 cohort 才能计算，T7 只做"早停/继续"判断，不做最终结论；这修正了 v1.1 把"每周≥3 次"与"7 天 cohort"并置的周期错配。

- 每日次数存本地，清空 `localStorage` 即可重置。**接受**：这是朋友间的游戏，不设服务端反作弊。
- 分享卡不包含种子、食物序列、路径，防止"照着答案刷分"。
- 连续天数只认"当日得分 ≥ 10"（至少吃到一个食物），避免开局自杀刷天数。
- cohort 数据由参与者自报/录屏，存在霍桑效应；目标值只用于方向判断，不用于对外宣称。

### 7.0 全局规则

#### 7.0.1 模式

| 模式 | 入口 | 随机性 | 记录 | 分享 |
| --- | --- | --- | --- | --- |
| **每日挑战** | ready 态主按钮 | 日期种子 | 每日最佳、剩余次数、连续天数 | 可分享 |

#### 7.0.2 状态机

| 当前状态 | 事件 | 下一状态 | 说明 |
| --- | --- | --- | --- |
| `ready` | 开始 | `running` | 方向键 / 空格 / 点击 / 滑动 |
| `running` | 暂停 | `paused` | 手动（空格）或自动（切标签/失焦） |
| `paused` | 继续 | `running`（手动）/ `countdown`（自动） | 自动暂停先走 3-2-1 |
| `countdown` | 倒计时结束 | `running` | 输入忽略，不会死亡 |
| `running` | 死亡 | `over` | 撞墙 / 咬到自己 / 主动结束 |
| `running` | 棋盘填满 | `won` | 停止推进，显示满分 |
| `over` / `won` | 重开 | `running` | 分数归零 |

- `ready`：未开始；overlay 可见。
- `running`：模拟推进；overlay 隐藏；HUD 实时更新。
- `paused`：模拟冻结；overlay 显示"已暂停"。
- `countdown`：恢复前的 3-2-1；输入被忽略；不会死亡。
- `over`：死亡或主动结束；overlay 显示本局分数、今日最佳、死因。
- `won`：棋盘填满；只可能出现在极小棋盘或理论极限。

#### 7.0.3 全局交互规则

| 输入 | ready | running | paused | 倒计时 | over | won |
| --- | --- | --- | --- | --- | --- | --- |
| 方向键 / WASD | 开始并转向 | 入队 | 忽略 | 忽略 | 忽略 | 忽略 |
| 空格 | 开始 | 暂停 | 继续 | 忽略 | 再来一局 | 再来一局 |
| R | — | 暂停并提示"再按 R 重开"；每日模式只暂停 | 重开；每日模式无效 | 忽略 | 重开 | 重开 |
| M | 静音切换 | 静音切换 | 静音切换 | 静音切换 | 静音切换 | 静音切换 |
| 点击/轻触棋盘 | 开始 | — | — | — | — | — |
| 滑动 | 开始并转向 | 转向 | 忽略 | 忽略 | 忽略 | 忽略 |

**全局约束**

- 所有键盘操作在 `keydown` 处理，忽略 `event.repeat`。
- 方向输入与当前方向相反、或与队列末尾相同，一律拒绝（沿用 v1.0）。
- 输入队列上限 2；队列满时新输入丢弃，不报错。
- 页面隐藏（`visibilitychange`）自动暂停；窗口失焦（`blur`，P1）同样暂停，100ms 防抖；恢复时若为自动暂停，先倒计时。
- 游戏结束/胜利后，模拟不再推进。
- 所有持久化失败（隐私模式、配额满）都降级为内存态，不阻断游戏。

### 7.1 R1 · 每日挑战

**用户故事**

> 作为一个每天只有一分钟的玩家，我想打开就有一局"今天所有人一样"的挑战，这样我有理由明天再来，也能和朋友比一比。

#### 7.1.1 规则

| # | 规则 | 说明 |
| --- | --- | --- |
| R1.1 | 日期 | 使用设备本地日历日 `YYYY-MM-DD`；跨午夜时，已开始的对局归属开始日 |
| R1.2 | 种子 | `seed = FNV-1a32("snake:v1:" + date)`；随机源为 `mulberry32(seed)` |
| R1.3 | 开局 | 每次尝试都用同一日期种子重新初始化；初始蛇、初始食物一致，相同占用状态下的食物抽取结果一致 |
| R1.4 | 次数 | 每天 3 次；**死亡或主动结束**时扣 1；开始时不扣 |
| R1.5 | 次数用尽 | 禁止开始新的每日对局；空格、R、点击、滑动均不开始新局；显示距本地午夜的倒计时；练习模式仍可用 |
| R1.6 | 每日最佳 | `best = max(当日所有已完成对局)`；分享卡使用每日最佳；每日模式 HUD 的 `BEST` 显示当日最佳，练习模式显示历史最高；任一模式破纪录都写入全局 `snake:best` |
| R1.7 | 连续天数 | 仅当当日得分 ≥ 10 时结算：昨天玩过则 +1，今天已计过则不变，日期断档则从 1 开始；得分 <10 不计入、也不清零 |
| R1.8 | 主动结束 | 暂停态提供"结束本局"；在每日模式中视为一次完成，扣次数，分数计入当日最佳 |
| R1.9 | 重开限制 | 每日模式运行中按 R 只暂停，不直接重开；必须"结束本局"后再开新的一次 |
| R1.10 | 损坏数据 | JSON 解析失败/字段缺失/越界 → 重置当日状态，不崩溃，不覆盖全局最高分 |
| R1.11 | 清理 | 启动时删除 7 天前的 `snake:daily:v1:*`，避免 localStorage 膨胀 |
| R1.12 | 时钟异常 | 系统日期非法或回拨：当日键取合法值；无法判断时按今天处理，不阻塞游戏 |

#### 7.1.2 确定性边界（重要）

"同一开局"的准确含义是：

- **相同日期 + 相同初始状态 + 相同逐步输入序列 ⇒ 相同蛇身、食物、分数。**
- 由于食物只在空格中生成，**不同走法会导致后续食物位置不同**。本版不承诺"不同玩家在任何走法下看到完全相同的食物序列"。

这是有意的取舍：要做到逐帧同一关，需要预计算与占用无关的食物序列，复杂度和收益不成正比；而分数比较在同一初始难度下仍然成立。

#### 7.1.3 验收标准

| # | Given | When | Then |
| --- | --- | --- | --- |
| AC1.1 | 日期 D，两个全新游戏实例，同一 RNG 种子 | 输入相同的 200 步方向序列 | 每一步后的 `snake`、`food`、`score`、`interval` 完全一致 |
| AC1.2 | 日期 D，`attemptsLeft=3` | 玩家死亡 | `attemptsLeft=2`，`runs+1`，`best=max`，写入 `snake:daily:v1:D` |

#### 7.1.4 边界情况

- 跨午夜时死亡：按 `runDate` 写入旧日期，连续天数按 `runDate` 计算；今天的记录不受影响。
- 系统时区改变：日期键随之改变；不做补偿，文档说明。
- 同一天内多次修改系统时间：以当前合法日期为准；可能导致多次"今日"记录，接受。
- `localStorage` 满：写失败时保留内存态，提示一次"记录仅保存在本次会话"。
- 隐私模式：同上。

## 10. 技术约束与实现要点

> 本节不是详细设计，只锁定"不能违背的架构决策"和"必须提前想清楚的算法边界"。详细实现由工程在 plan 阶段展开。

### 10.1 架构原则

1. **规则与渲染分离**：`game.js` 不碰 DOM、不读时钟、不直接用 `Math.random`；随机源注入。
2. **零依赖、无构建**：新增代码仍是原生 ES modules；测试用 `node --test`。
3. **纯函数优先**：种子、日期键、连续天数、分享文案等可单测的逻辑不依赖浏览器。
4. **渐进增强**：PWA、分享、音效都是增强；核心玩法在最低配置下仍可玩。
5. **配置集中**：所有数值进 `config.js`，不散落魔法数字。

### 10.3 数据模型

```json
// snake:daily:v1:2026-10-20
{
  "attemptsLeft": 2,
  "best": 240,
  "runs": 1
}

// snake:streak:v1
{ "count": 4, "lastDate": "2026-10-19" }
```

字段约束：

- `attemptsLeft`：整数 0–3；越界钳制。
- `best`：非负整数；与全局 `snake:best` 独立。
- `runs`：非负整数；用于"是否完成过今日"与分享资格。
- `lastDate`：`YYYY-MM-DD`；非法则视为无记录。

### 10.4 关键算法

**日期种子**

```js
function fnv1a32(str) {
  let h = 0x811c9dc5;
  for (let i = 0; i < str.length; i += 1) {
    h ^= str.charCodeAt(i);
    h = Math.imul(h, 0x01000193);
  }
  return h >>> 0;
}

const seed = fnv1a32(`snake:v1:${date}`);
```

**可复现随机源**

```js
function mulberry32(a) {
  return function next() {
    a |= 0;
    a = (a + 0x6d2b79f5) | 0;
    let t = Math.imul(a ^ (a >>> 15), 1 | a);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}
```

**每日开局**

```js
const game = new SnakeGame(CONFIG, mulberry32(seed));
game.startDaily(runDate); // 记录归属日，不改变初始状态
```

**连续天数更新（完成时）**

```js
if (score < 10) return;                 // 不计入
if (state.lastDate === today) return;   // 今天已计
if (state.lastDate === yesterday) count += 1;
else count = 1;
state.lastDate = today;
```

**展示连续天数**

```js
if (lastDate === today || lastDate === yesterday) return count;
return 0; // 不写盘；下次得分 ≥10 时从 1 开始
```

**次数扣减（结束时）**

```text
attemptsLeft = max(0, attemptsLeft - 1)
best = max(best, score)
runs += 1
```

### 10.5 Service Worker 策略

- 缓存名：`snake-v1.1.0`；发布时随版本号递增。
- 预缓存：`./`、`index.html`、`css/style.css`、全部 `js/*.js`、`manifest.webmanifest`、图标、OG 图。
- 导航：`network-first`，3s 超时回退缓存 `index.html`；确保新版本能尽快替换旧 HTML。
- 静态：`cache-first` + 后台更新；只处理 `request.method === 'GET'` 且同源。
- 更新：`install` 不 `skipWaiting`；`message SKIP_WAITING` 后激活；`controllerchange` 在非 running 状态刷新，running 时挂起。
- 清理：`activate` 删除非当前版本缓存。
- 排障：`?sw=off` 注销并清空缓存。
